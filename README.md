MC 汉化工坊基于 Tauri v2 + React + TypeScript + Rust 构建，当前发布 Windows x64 安装包，其他平台可从源码自行构建。

把内容包拖进窗口（模组 jar / 服务器插件 jar / 光影包 zip / 资源包 zip / 整合包 zip 或 **`config/ftbquests` 任务书文件夹**），程序自动解析可翻译文本，结合上下文完成 AI 汉化，再导出为汉化 jar、光影包、资源包，或直接写回任务书的章节文件。切换到「游戏目录」模式可直接扫描 `.minecraft`，按游戏版本批量导入上千个内容包，列表按「**游戏版本 → 内容包 → 具体条目**」三级组织，折叠的内容不渲染。

![主界面](docs/主界面.png)

> **⚡ 实测速率**：付费模型智谱 `glm-4.5-air` + 并行加速，约 **110 秒**完成 3 个内容包共 350 条翻译。
> 实际速率因模型、网络与服务商限流而异；**免费模型大概率因限流无法开启并行与内容包并行**，建议单线程或低并发使用。

## 快速开始

1. **下载安装**：从 [Releases](https://github.com/adssadax-1/mc-content-localizer/releases) 下载 Windows x64 安装包（NSIS 或 MSI），或 clone 源码自行构建。
2. **配置服务**：右上角「设置」→ 选择服务商 → 填入 API Key → 获取模型列表 → 选择模型 → 保存。用本地模型（Ollama / llama.cpp）则免 Key。
3. **导入内容包**：把文件拖进窗口，或点击中央区域选择。拖入**文件夹**时程序先判断它是不是任务书目录（`config` / `ftbquests` / `quests`），是则直接解析任务书，否则切到「游戏目录」模式逐级扫描。整合包 zip 会先检测其中的任务书，检测不到才按普通压缩包处理。

![内容包导入](docs/内容包导入.png)

4. **开始翻译**：勾选需要翻译的内容包，点击「开始 AI 翻译」，进度条实时估算剩余时间。

翻译过程中条目按状态实时着色（翻译中 / 已汉化 / AI 未返回 / 翻译失败）：

![翻译条目状态区分](docs/翻译条目状态区分.png)

结束后汇总本次结果与针对性建议：

![翻译错误提示](docs/翻译错误提示.png)

5. **人工审校**：表格里点击译文即改；单元格右侧可单条清除重译；工具栏「清除 ▾」可清空当前类型列表或清除勾选的内容包。

![清除译文界面](docs/清除译文.png)

按住表格行内空白处（原文 / key / 状态列）上下拖动可框选批量勾选，从已勾选行开始拖则批量取消，拖到边缘自动滚动（复选框、按钮、输入框等交互元素不触发框选）：

![快速拖动选择](docs/快速拖动选择.gif)

6. **导出**：点击「导出」，按勾选内容的类型自动分流——
   - **模组**：合并汉化资源包（一个 zip 管所有勾选模组）/ 汉化 jar（不覆盖原文件）
   - **服务器插件**：汉化 jar（`plugins/<插件名>_zh_cn.jar`，YAML 保持注释与键序）
   - **光影包**：`xxx_zh_CN.zip`；**资源包**：改描述后的资源包
   - **任务书**：磁盘来源直接**写回原文件**（首次写回自动备份 `.zhbak`）；整合包 zip 来源另存 `_zh_cn.zip`
   - 文件名跟随「导出命名偏好」（原名 / 原名_zh_cn / AI 汉化名称），同名自动加序号；导出完成的通知里可一键打开所在文件夹

> 1.12.2 及更早版本若游戏内中文显示为方块，需要自行安装字体修复类资源包（与本程序无关）。

### 顶栏即时开关（主题 / 语言 / 无字模式）

右上角三个按钮直接切换外观，点一下即改，不必先进设置再保存；图标本身表达当前状态：

- **主题**：亮色 / 暗色（太阳 / 月亮）
- **语言**：按钮显示当前语言码（ZH / EN），点开即切
- **无字模式（只留图标）**：把顶栏、侧栏、主工具栏、页脚的文字原地收起只留图标，给窄窗口和内容本身腾地方；内容区（译文表格、术语表、卡片）一字不动，所有图标按钮都有悬停名称与读屏名

![无字模式 · 主界面](docs/无字主页面.png)

![无字模式 · 服务商设置](docs/无字服务商设置页面.png)

### 个性化设置

设置 →「个性化设置」只留「需要想一下、适合一并保存」的几项——主题与语言已移到顶栏即时开关，深度扫描另立设置页：

![个性化设置](docs/个性化设置.png)

- **自动记录日志**（默认开启）：把本次运行的解析 / 翻译 / 导出 / 报错记到软件自己的数据目录；关掉只停止记录，**不会删除已有日志**
- **导出命名偏好**：原名（与源文件同名，可直接替换加载）/ 原名_zh_cn（默认）/ **AI 汉化名称**（翻译时让模型起一个简洁中文名，如 `机械动力_汉化.jar`；只有这一档才会产生额外的命名请求）
- **关闭行为**：直接退出，或最小化到托盘（托盘菜单可恢复窗口 / 退出）
- **记住上次停留的设置分组**：关闭设置再打开会回到上次那一页（只记住页面，不写入磁盘）

### 会话恢复

内容包列表自动缓存：软件崩溃、意外关闭或正常退出后再打开，会询问是否恢复上次的列表（含译文与进度）。缓存**按内容包分片存储**，只重写发生变化的那一片，恢复不依赖原包文件仍在。

![会话恢复](docs/会话恢复.png)

### 游戏目录模式

顶栏切换到「游戏目录」，选择 `.minecraft`、`versions` 或任意文件夹，程序递归找出所有版本分组（模组 / 插件 / 资源包 / 光影包 / 任务书分列计数）；直接指向 `mods`、`resourcepacks`、`shaderpacks` 或任意内容包文件夹也能识别（`.jar` / `.zip` 按内容自动分类）。

![游戏目录扫描导入](docs/游戏目录扫描导入.png)

左侧版本行可整体勾选，分类与选择面板均可折叠展开、旁边勾选框全选对应范围；勾选后「解析并加入列表」逐包入队，后续翻译、导出与自由导入一致，跨版本、跨包译文自动复用，导出自动按版本建子目录。

扫描结果会缓存（内存 8 条 + 落盘 `scan-cache-gamedir.json`），切回「最近目录」不再重跑进度条，重启软件也不必重扫；左栏常驻「扫描于 14:52」与「缓存」标签标明结果来源与时间。「重新扫描」忽略缓存强刷当前目录，失败或被取消时保留旧结果与旧缓存。

> 扫描缓存是**按目录**缓存的，升级后任务书等新识别项不会自动出现在旧缓存里 —— 点一次「重新扫描」即可。

### 内容包列表：三级树

从游戏目录加入的内容按「**游戏版本 → 内容包 → 具体条目**」三层组织：版本父级行可展开/折叠，展开后是该版本的内容包卡片，卡片再展开才是条目表格。**直接导入**的内容包（jar / zip / 文件夹 / 任务书）不套版本层，仍是「内容包 → 条目」两层，与游戏目录的内容之间有一条分隔线区分。

![内容包列表三级树](docs/三级树.png)

- **按需渲染**：折叠的版本不创建任何内容包卡片、折叠的卡片不创建条目表格 —— 上千个内容包全部折叠时，界面上只有若干行版本父级
- **父级勾选框**：三态（全选 / 半选 / 未选），一键全选或取消该父级**当前筛选范围内**的全部内容包；筛选之外的隐藏内容不受影响
- **默认折叠、不自动展开**：导入后不展开、搜索命中也不展开，展开与否只由点击决定；展开状态按内容类型分别记忆
- 切换内容类型时父级行按序错峰入场

## 任务书

整合包的任务书（FTB Quests）文本不在语言文件里，而是**内联**在 `config/ftbquests/quests/` 的 SNBT 文件中。程序把它作为第五类内容包处理，与模组、资源包、光影包、插件并列，并按「**整合包 → 章节（内容包）→ 条目**」组织：

![任务书](docs/任务书.png)

- **导入**：游戏目录扫描自动识别并归入所属版本；也可以直接拖入整合包 zip，或直接拖入 `config` / `ftbquests` / `quests` 文件夹。整合包 zip 的检测判据是「存在 `…/ftbquests/quests/chapters/*.snbt`」——光影 / 资源包 / 普通模组 / 普通压缩包都不会被误判；检测不到就完全走原有导入逻辑
- **层级**：任务书的最上层父级是**整合包名**（不是游戏版本号），三种导入方式一致；实例目录名形如 `1.21.11-Fabric 0.19.2` 时自动改用任务书标题。父级带勾选框，可一键全选/取消该整合包当前筛选范围内的全部章节
- **导出**：按条目指针**原位写回**章节 SNBT；整合包 zip 来源不写回原包，而是另存 `_zh_cn.zip`
- **格式码预览**：原文与译文都支持 `&` / `§` 颜色与格式码的悬停预览 —— 上图里鼠标停在 `&eXray - …` 上，弹出的深色提示框就是渲染后的真实效果

<details>
<summary>点击展开：任务书的解析范围与导入细节</summary>

**会被提取为可翻译条目的字段**（只读 `chapters/*.snbt`）：

| 位置 | 字段 | 说明 |
|---|---|---|
| 章节文件根级 | `title` | 章节标题 |
| 每个任务 | `title` / `subtitle` | 任务标题与副标题 |
| 每个任务 | `description[]` | 任务描述，逐行成条（空行自动跳过） |
| 图片元素 | `hover[]` | 图片悬停提示文本 |

条目 key 形如 `chapters/0_getting_started.snbt#quests[3].description[1]`——文件相对路径 + 指针，因此写回时能精确落到那一行文本上。

**暂未纳入翻译的文本**：任务书总标题（`data.snbt` 的 `title`，目前只作为「整合包父级」的展示名）、章节分组名（`chapter_groups.snbt`）、奖励表标题（`reward_tables/*.snbt`）。

**写回是怎么做的**：SNBT 不是标准 JSON（键可不带引号、元素以换行分隔），所以程序**不做结构化重排**，而是解析时记住每个字符串的字节区间，写回时按区间原位替换 —— 任务 ID、依赖关系、缩进与排版一字不动。首次写回前会把原文件备份为 `<文件名>.snbt.zhbak`。

**专属提示词**：任务书使用独立的提示词模板（叙事文风 + `&` 色码 / `{@pagebreak}` 分页标记保留 + 逐行结构保留），可在「自定义提示词 → 任务书」里改成自己的版本，与模组等类型互不混用。

## 深度扫描

深度扫描用于挖掘「常规解析」之外的内嵌文本（成就、配置、代码常量等）。它由一组**可逐条开关的规则**控制，模组与插件各持一套：

| 分组 | 规则 | 默认 |
|---|---|---|
| 扫描范围 | 扫描 JSON / `.lang`、`.properties` / 配置文件与文本 / 递归嵌套 jar / 提取 `.class` 代码内文本 | 代码内嵌：插件开、模组关 |
| 路径与语种 | 跳过元数据与许可文件 / **跳过语言文件本体（固定开）** / 跳过打包进来的第三方库 / 只取源语言与中文 / **中文一律保留（固定开）** | 全部开启 |
| 文本过滤 | 丢弃 SQL / 方法签名 / 日志句式 / 纯标识符 / 代码文本按可见性分级 | 全部开启 |

- **模板**：`推荐`（默认）、`精简`（只扫常规文本）、`全量（旧行为）`（含代码内嵌、关闭全部降噪过滤）
- **单包覆盖**：内容包卡片上悬停扫描按钮可见当前规则摘要与「本包含单独配置」；点齿轮为该包单独调整（只保存与全局的差异）。单包配置是**临时性**的：只保留在内存、不写入设置文件，重启或重新导入即回到全局规则；弹窗左下角「跟随全局设置」可一键清除
- **重扫合并**：按条目 key 合并，已有译文与勾选状态全部保留；规则变更后不再产出的条目若已有译文会保留并标注「规则已排除」
- **固定项**：嵌套深度 3 层、文本长度 3–200、「文本得像个可翻译的句子」的打分门槛，以及「单个词的标签需与 `Armour: ` 前缀同处一个类」这条闸门，都由引擎固定，不对外开放以免误调。**这也是「全量（旧行为）」不会给出一切的原因** —— 全小写词、纯标识符、没有前缀陪伴的孤立单词，切模板也不会出现

内容包卡片上的深度扫描按钮（悬停后出现齿轮，齿轮即单包规则入口）：

![单包深度扫描](docs/单包深度扫描.png)

设置 →「深度扫描」里模组与插件各有独立入口，点开即配置（顶部为「自动深度扫描」总开关，下面是三组规则、模板与自定义规则）：

![深度扫描设置页面](docs/深度扫描设置页面.png)

规则弹窗（以模组为例）：「内置规则 / 自定义规则 / 规则测试台」三个标签页，每条规则都带一句说明（扫什么、什么代价），锁定项标注为固定开启：

<details>
<summary>点击展开：代码内嵌文本（<code>.class</code>）支持范围</summary>

- **解析对象**：jar 内（含 `META-INF/jars/` 里嵌套 jar）所有 `.class` 文件的**常量池**——按 JVM 规范只读 `CONSTANT_Utf8` 字符串字面量，不加载类、不反编译，因此不需要该 jar 能运行、也不受 Java 版本影响
- **能提取到什么**：编译进代码的玩家可见文本——聊天与命令反馈、GUI/菜单标题与按钮、物品与计分板名称、Boss 血条与 Tab 标题、提示语与报错提示（带 `§`、`&a` 颜色码或 `%s`、`{0}` 占位符的最典型）
- **默认会被过滤掉什么**（「推荐」模板）：JVM 方法签名与类型描述符（`(...)V`、`Lnet/…;`）、SQL 语句、日志句式（`failed to load…`）、纯标识符/键名/权限节点、`minecraft:` 命名空间与 URL/路径样式、纯数字或纯 kebab/snake id、长度不在 3–200 字符内的，以及被打包进来的第三方库类（`bukkit/`、`google/`、`kotlin/` 等，由「跳过库类」规则控制）。**含中文的文本一律保留**
- **可见性分级**：开启「代码文本按可见性分级」后，含颜色码/占位符、本身就是成句（≥8 字符且含空格）、以及 `Armour: ` 这类**标签前缀**的文本，都归入「消息文本」组并**默认勾选**；**单个词的按钮文字**（`Armour` / `Shown` / `Glint` / `Nametags`…）只在同一个类里还存在这类前缀时才一并放行 —— 否则 NBT 与数据键（`Name`、`Color`、`Lore`、`SkullOwner`）会成批混进来，它们和按钮文字长得一模一样，被翻译后会让 `getString("Name")` 这类查表静默失配。其余归入「代码内嵌·其他」默认不勾选
- **默认开关**：插件**默认开启**（插件消息大多硬编码在代码里）；模组**默认关闭**（模组文本多数在语言文件内）。想尽可能少过滤，可切「全量（旧行为）」模板
- **⚠️ 资源包改不了这类文本**：资源包能覆盖的只有 `assets/<modid>/lang/` 下的语言文件。**写死在 `.class` 代码里的文字，无论怎么做资源包都不会生效** —— 唯一可行的路径是「导出汉化 jar」+ 打开「内嵌文本改写」。所以用合并资源包汉化某个模组时若发现按钮、提示仍是英文，先确认它不是被写死在代码里（见「常见问题 → 为什么有些文本没被扫到」第 3 条）

</details>

<details>
<summary>点击展开：规则档案（社区分享）的格式与校验</summary>

规则集可导出为 JSON 档案并分享给他人，格式如下（`rules` 与设置文件中的 `deepScanRules` 结构一致）：

```json
{
  "version": 1,
  "kind": "plugin",
  "name": "某服务器插件常用规则",
  "note": "面向 Bukkit 系插件，已过滤库类与日志句",
  "rules": {
    "scopeJson": true, "scopeLang": true, "scopeText": true,
    "scopeNested": true, "scopeClass": true,
    "skipMeta": true, "skipLangfiles": true, "skipLibs": true,
    "onlySourceLocale": true, "keepCjk": true,
    "dropSql": true, "dropDescriptor": true, "dropLog": true,
    "dropIdent": true, "classNeedsMarker": true,
    "custom": [
      { "id": "c1", "name": "SNBT 数据", "enabled": true, "kind": "ext",
        "pattern": "snbt", "action": "include", "source": "imported" },
      { "id": "c2", "name": "排除测试文本", "enabled": true, "kind": "textRegex",
        "pattern": "^(test|debug)", "action": "exclude", "source": "imported" }
    ]
  }
}
```

导入时程序会校验：档案版本不得高于当前支持版本、`kind` 必须与当前类型（模组 / 插件）一致、自定义规则逐条校验（正则语法、扩展名不得是二进制类型、名称与模式长度上限），非法规则被剔除并给出提示，内置规则整体套用。导入后的自定义规则与手写规则同等对待，可随时开关或删除。

</details>

## 翻译能力与加速

<details>
<summary>点击展开：并行加速、批次策略与译文质检</summary>

设置 →「翻译加速」：

![翻译加速设置](docs/翻译加速.png)

- **并行加速（线程数 1-8 + 请求间隔）**：并行发送翻译请求；间隔越大越不容易触发限流（推荐 ≥ 4s）
- **每批条数自动最优（默认开启）**：每批条数 = 待翻译条目数 ÷ 线程数；条目过少导致批次过小时会主动提醒
- **内容包并行翻译**：同时翻译 2 / 4 / 8 个内容包或无限制，每个内容包独立实时进度与完成提示
- **风险提示**：**免费模型大概率因限流无法开启并行与内容包并行**——免费模型通常有账号级速率限制，多线程 / 多包并发容易触发 429（程序会自动退避重试）。参考：OpenRouter 免费模型可开 8 线程，智谱免费模型（glm-4-flash 系列）建议 1-2 线程，付费模型可开 4-8 线程

翻译流水线本身还包含：跨内容包译文复用（相同原文直接复用，不重复调用）、占位符与格式码校验（丢失或改序会标在备注列）、「译文与原文相同」检测与一键清除重译、失败自动重试 + 429 退避、翻译期间按内容包分片落盘。

</details>

<details>
<summary>点击展开：术语表与自定义提示词</summary>

- **用户术语表**（设置 →「术语表」）：`原文 → 译文` 键值对，翻译时作为硬约束注入提示词，用于锁定专有名词译名
- **「先提取术语表」开关**（同一分组内，默认开启）：翻译前让模型从内容包中提取术语；关闭即完全不提取。提取结果在翻译完成汇总弹窗里勾选「加入术语表」，建议的高频词也可一键入表
- **自定义提示词**（「术语表」分组底部的按钮打开）：**五类内容各一套**（模组 / 光影包 / 资源包 / 服务器插件 / 任务书）分开定制，「可编辑段」开放修改、「核心段」（占位符规则、术语表注入、输出格式）系统锁定只读；支持一键恢复默认，改过的类型会显示「已定制」标记

</details>

模型列表是可搜索下拉、免费模型带「免费」标注并优先排序；预设服务商的 Base URL 只读展示并附官网跳转；「验证连接」可一键检测所选 Key + 地址 + 模型是否可用。

<details>
<summary>点击展开：本地模型（Ollama / llama.cpp）</summary>

预设里带两家本地推理服务，**不用填 API Key**，模型名由你本地已拉取的模型决定：

| 服务 | 默认地址 | 说明 |
|---|---|---|
| Ollama | `http://localhost:11434/v1` | 模型名取自 `ollama list`；地址可改端口或走局域网 |
| llama.cpp | `http://127.0.0.1:8080/v1` | `llama-server` 默认免鉴权；模型名取自启动参数里的 `--alias` |

本地档做了几处针对性处理：

- **不发送 Authorization 头**：本地服务端本来就不校验；Key 留空即可保存，切回云端档时仍会要求填 Key
- **绕过系统代理**：机器上开着代理工具时，发往本机端口的请求不再被代理劫持（此前表现为本地模型莫名连不上）
- **超时放宽**：本地推理冷启动要加载权重、单并发还要排队，单请求超时比云端档宽松
- **响应解析更宽容**：不要求模型返回"完美 JSON"——带代码块围栏、夹着解释文字、甚至被截断的输出都能尽量读出可用条目；不回显条目 key、直接给原文也能对上；key 的大小写与空格差异不再导致漏条
- **批次自动补漏**：整批「有返回但不可用」时，只把未拿到的条目重发一次并追加更严格的格式要求
- **未翻译原因可辨**：备注列能区分「模型没有返回」与「返回了但内容不可用（具体原因）」

</details>

## 数据与缓存

- **API Key 存储**：仅保存在本机配置文件（`%APPDATA%/com.administrator.mod-translator/settings.json`，macOS 为 `~/Library/Application Support/...`），不上传至任何第三方、不入仓库。日志会记录运行过程，但**写入前会把 Key 在内的敏感信息替换成 `***`**
- **翻译内容**：条目文本仅发送给你自己选择的服务商用于翻译
- **翻译质量提示**：AI 翻译仅供参考，建议导出前人工审校；专有名词可通过术语表锁定译名
- **设置损坏会被留档**：若 `settings.json` 解析失败，程序会先把它改名成 `settings.corrupt-<时间戳>.json` 再用默认值启动，原始内容不会被静默清掉

<details>
<summary>点击展开：本地数据位置与清理入口</summary>

程序不会往安装目录写任何文件，全部数据都在当前用户目录下（`<用户名>` 替换为你自己的账户名）：

| 位置 | 内容 | 大小 | 说明 |
|---|---|---|---|
| `%APPDATA%\com.administrator.mod-translator\settings.json` | 设置：API Key、模型与服务商、术语表、自定义提示词、翻译参数、主题语言、最近游戏目录、关闭行为 | 十几 KB | **不是缓存，是用户数据**。删除等于全部设置与 Key 重置 |
| `%APPDATA%\com.administrator.mod-translator\session-free-shards\` | 会话缓存：`index.json`（列表顺序 + 分片索引）与每个内容包一个分片文件（原文、译文、备注、勾选状态） | 与内容包数量成正比，每包几十至几百 KB | **唯一保存翻译成果的缓存**。崩溃或意外关闭后再次打开会询问是否恢复 |
| `%APPDATA%\com.administrator.mod-translator\logs\` | 会话日志：一次运行一个 `session-<年月日>-<时分秒>.log` | 每次运行几十 KB | 记录解析、翻译、导出、报错等过程（已脱敏） |
| `%APPDATA%\com.administrator.mod-translator\session-cache-free.json` | 旧版（≤ v2.3.x）整份会话缓存 | 可能几十 MB | 仅从旧版本升级上来时残留，可安全删除——v3.0.0 起改用上面的分片缓存 |
| `%LOCALAPPDATA%\com.administrator.mod-translator\EBWebView\` | 内嵌浏览器（WebView2）的缓存：网页缓存、GPU 着色器缓存、崩溃转储等 | 几十至一百多 MB（随使用增长） | **不含任何翻译数据**，可安全删除，程序会自动重建（首次启动略慢） |

**导出产物**不在上面：导出时会让你选择目录，文件写在你指定的位置。想保留译文与设置，备份 `%APPDATA%\com.administrator.mod-translator\` 整个目录即可（注意 `settings.json` 中 API Key 为明文，勿随意外传）。安装包卸载时不会自动删除上述目录，可在卸载前用「清除用户数据」先清干净。

![关于页的本地数据清理](docs/关于设置页面清除数据功能.png)

「关于 → 本地数据」面板上会显示缓存 / 用户数据 / 日志各自占用与数据目录（可一键复制），并提供两档清理：

- **清除缓存**（1 次确认）：删会话缓存（上次的内容包列表快照）、游戏目录扫描缓存与 WebView2 浏览器缓存；设置、API Key 与已导出的产物都不受影响。会话快照删掉后，下次启动不会再询问「恢复上次列表」

  ![清除缓存弹窗](docs/清除缓存弹窗.png)

- **清除用户数据**（2 次确认）：连 API Key、全部设置、术语表、AI 命名缓存一并删除，等于回到全新安装状态；完成后提示释放空间并提供「立即重启」。**日志默认不在删除范围内**，要一起删就在第二步勾上「同时清除日志」

  ![清除用户数据第一步](docs/清除数据第一次弹窗.png)

  第二步是最后一道闸门：标题直接问「你确定你在干什么吗？」，**必须勾选「我已确认：删除以上全部数据，且无法恢复」，「执行清除」按钮才可点击**：

  ![清除用户数据第二步确认](docs/清除用户数据第二次确认弹窗.png)

两档都**只作用于软件自己的数据目录**（上表两处，由程序按应用标识符解析，不接受任何外部路径）：游戏目录、导出目录、其他软件的文件一律不会被触碰。程序还会逐个校验目标路径确实位于这两个目录之内，路径不合法的一律跳过，被占用的条目跳过并在界面如实提示。

## 常见问题

<details>
<summary>Q：为什么有些文本没被扫到？</summary>

**先明确一点：文本扫不到，绝大多数是扫描规则的问题，而不是程序坏了。** 解析范围完全由你当前的规则决定 —— 规则里没打开的东西，程序不会去找它。按下面顺序排查，基本都能自己定位：

1. **它可能本来就不该出现** —— 写死在 `.class` 代码里的文字、纯配置项、SQL 语句、日志句式、权限节点之类，要么没有翻译价值，要么常规解析够不到（代码内嵌默认不扫，见第 3 条）
2. **被「推荐」模板的降噪规则过滤了** —— 默认会丢弃第三方库类文本、SQL、方法签名、日志句式、纯标识符等噪声。想尽可能少过滤，把该类型的模板换成「**全量（旧行为）**」，或针对具体路径加一条「包含」规则
3. **模组的 `.class` 内嵌文本默认关闭** —— 模组文本大多在语言文件里，所以代码常量默认不扫。需要就去「深度扫描 → 模组」把「提取 `.class` 代码内文本」打开
4. **扫描范围没覆盖这个文件类型** —— 「扫描范围」组里 JSON、`.lang` / `.properties`、配置文件与文本、递归嵌套 jar 各自独立开关；非常规扩展名要在「自定义规则」里加一条「包含」规则
5. **自定义规则把它挡掉了** —— **排除优先于包含**：只要命中任意一条「排除」规则就会被挡下，哪怕同时命中了「包含」。翻译表格里 Key 悬停会列出「命中该路径的已有规则」，被上级目录的排除规则覆盖时面板也会直接写明
6. **任务书只扫章节文件** —— 任务书总标题、章节分组名、奖励表标题目前不在翻译范围内（见「任务书 → 解析范围」）
7. **游戏目录用的是旧扫描缓存** —— 缓存里没有的类型（如升级后新增的任务书）不会自动出现，点一次「重新扫描」

**判断标准**：把该类型的模板切到「全量（旧行为）」、并把「自定义规则」里可疑的排除项逐个停用，再**重新扫描一次**。如果内容仍然不出现，那才是软件的问题 —— 这时请带上日志反馈（左下角「日志」→「导出本次会话」），能省下大量来回。

</details>

<details>
<summary>Q：免费模型翻译老是失败 / 报 429？</summary>

免费模型通常有**账号级并发与频率限制**，多线程或内容包并行很容易触发。建议：把线程数降到 1-2、内容包并行关掉、请求间隔调大（≥ 4s）。程序自身对 429 有自动退避重试与批次补漏，但仍受服务商额度限制。想要速度就换付费模型（智谱 `glm-4.5-air` 等）或本地模型。

</details>

<details>
<summary>Q：导出后在游戏里没生效？</summary>

按类型检查：

- **模组 jar**：生成的是新文件（不覆盖原 jar），需要自己替换 `mods/` 下的原文件
- **合并资源包**：把 `mods_zh_cn.zip` 放进 `resourcepacks/` 并在游戏里**启用**它；注意资源包只能覆盖 `assets/<modid>/lang/`，不影响其它文件。**写死在 `.class` 代码里的文字资源包永远覆盖不到** —— 那类文本只能走「汉化 jar」+「内嵌文本改写」这条路
- **服务器插件**：把 `plugins/<插件名>_zh_cn.jar` 放进 `plugins/`，并**删掉或改掉原插件 jar 的名称**（同名 jar 会冲突），或直接改名替换原文件
- **光影包**：`xxx_zh_CN.zip` 放进 `shaderpacks/` 后需在光影设置里重新选择
- **任务书**：写回模式下**改动的是整合包 `config/ftbquests` 里的原文件**，进游戏即生效；如果你在服务器 / 局域网联机，任务书内容以服务端为准

</details>

<details>
<summary>Q：升级后任务书没出现在游戏目录里？</summary>

游戏目录的扫描结果是**按目录缓存**的，旧缓存里没有任务书这一类。点左栏的「重新扫描」忽略缓存重扫一次即可；之后该目录就一直带着任务书了。

</details>

<details>
<summary>Q：出现「译文与原文相同」怎么办？</summary>

这是模型原样返回了原文（常见于短词、专有名词、或模型偷懒）。程序会自动检出并把原因写进备注列，可按备注列筛选后一键清除重译；也可以在术语表里为该词指定译名，或在条目上手动改。

</details>

<details>
<summary>Q：本地模型（Ollama / llama.cpp）连不上？</summary>

1. 确认服务已启动：Ollama 默认 `http://localhost:11434/v1`，llama.cpp 的 `llama-server` 默认 `http://127.0.0.1:8080/v1`
2. 换端口或跑在局域网另一台机器上时，把地址填进设置里的 Base URL（本地档的地址是可编辑的）
3. 程序已让发往本机端口的请求**绕过系统代理**；若你确实要走代理（例如服务在远端），改用「自定义服务商」填完整地址

</details>

## 版本记录

### v4.0.1（2026-10）

**新增：内嵌文本改写（导出汉化 jar 时可开）**

- 有一类文本以前**永远汉化不了**：作者把文字直接写在代码里（编译进 `.class`），语言文件和资源包都够不到它。本版新增开关「**内嵌文本改写**」（**默认关闭**；位置：设置 → 个性化设置）。打开后导出汉化 jar 时会真的把这些字改掉。
- **只管这一类条目**：原本就能生效的（语言文件键、`fabric.mod.json` 这类 JSON 里写死的名字/描述）**一个字都不碰**；**开关关闭时不做任何 `.class` 改写**，字节码原封不动 —— 所以它是"极端情况的兜底"，不是常规流程。
- 同时充当**字段名 / 方法名 / 枚举名**的文字会被自动跳过（改掉会让模组直接崩），导出统计里会列出跳过条数。
- 打开开关后，那些本来永不生效的 `.class` 条目**不再写进语言文件**，所以语言文件条数会明显变少 —— 这是正常的，不是内容丢失。

**修复**

- **插件汉化会把 `.class` 写坏**：此前插件导出误把二进制成员当文本处理，产出 jar 里的 class 文件已损坏（模组侧只是"翻译无效"，插件侧是"文件坏了"）。现已按类型区分，二进制成员原样保留。
- **键名带 `.` 的 JSON 翻译后不生效**：这类键被误当成多层路径，导致静默写回原文。现已修正。
- **被一层文件夹包起来的 jar 汉化不生效**：路径比对口径不一致，导致永远匹配不上。现已修正。
- **部分 `.class` 内嵌文本扫不出来**：常量池解析漏读了约一半条目，现已修正。
- **按钮上的单词标签扫不到，界面只汉化了一半**：像 `Armour` / `Shown` / `Scope: ` 这种**单个词的按钮文字**，因为没有空格也没有颜色码，被旧的降噪打分整条丢掉（表现为「悬停提示都汉化了，按钮还是英文」）。现已识别这类「Title 词」与「标签前缀」并把它们归入默认勾选的「消息文本」。**为避免把 NBT / 数据键（`Name`、`Color`、`Lore` 等）也一并扫进来**（它们同属"只被 `CONSTANT_String` 引用的 Title 词"，被翻掉会让 `getString("Name")` 这类查表静默失配），单词型标签**只在同一个类里还存在 `Armour: ` 形式的前缀时才放行** —— 实测可去掉约 95% 的这类噪声，而真实 GUI 类的标签一个不丢。
- **扫出一堆永远改不了的 JVM 内部名**：`Code` / `LineNumberTable` / `SourceFile` 这些属性名在常量池里也是字面量形态，过去会混进条目列表、白花翻译额度，却注定在改写时被拒。现在扫描与导出**共用同一把尺子**，只收「只被 `CONSTANT_String` 引用、且不被当作名字」的文本。
